# Handblock Printing Cloth — Website Review, 28 Oct 2026

Review only. No code was changed in this review. This is the separate
Next.js store in `~/workspace/handblock-printing-cloth`, not amberfabric.com.

## Verdict

Working, testable store, not yet a full production store. Core commerce is
sound: money in integer paise, server-side checkout recalculation, fabric
roll allocation, Razorpay payment + refund verified live on the user's
machine (see MEMORY). What is missing is mostly what happens *after* an
order is paid: shipping, fulfilment, email, and a complete admin order
workflow — plus real photos and a production database.

Tests run in this review: `npm test` — 11/11 pass (pricing, tiers, roll
allocation, tax/shipping, Razorpay signature + webhook signature).

## What works well

- Storefront: home, product list with search/category/type/price sort,
  product detail, cart, checkout, order tracking, wholesale, about, FAQ,
  shipping/returns/terms/privacy pages.
- Fabric by metre: 0.5 m steps, per-product min/max/increment, bulk tiers,
  shortest-single-roll allocation, continuous-cut block.
- Checkout: server recalculates price, tier, coupon, 5% tax, shipping
  (free ≥ ₹1,999 else ₹99), stock/variant deduction in one transaction.
  Frontend totals are never trusted. COD up to ₹10,000.
- Accounts: email/password, scrypt, httpOnly 30-day sessions, verification,
  forgot/reset, saved addresses, order history, password change, deletion
  requests. Guest checkout preserved, cart carries over after login.
- Payments: Razorpay Checkout, verify with HMAC + remote re-validation
  (captured, exact paise, INR, matching order id), webhook HMAC + replay
  guard, amount mismatch rejected, failed never downgrades paid.
  Live verified: HPC81634950 ₹2,352, HPC85166785 ₹1,275, HPC92350219 ₹771.
- Refunds: durable intents, admin issue/submit, Razorpay API when keys
  exist, manual-pending path otherwise, double-refund blocked, paid
  cancellation creates an intent only (no auto-submit).
  Live verified: HPC85166785 fully refunded ₹1,275.
- Admin: ADMIN_TOKEN-gated product create/edit/delete, rolls, CSV
  export/import, refunds page, recent orders + revenue + low rolls.

## Gaps — in priority order to make the website full

### 1. Shipping is not live (highest priority) — Bigship, not Shiprocket
- Update 28 Oct 2026: user chose Bigship instead of Shiprocket.
  Shiprocket is not to be used. Build Bigship integration instead.
- `src/lib/payments.ts` Shiprocket check is credential-gated and, even
  with credentials, only returns "serviceable: true" with no token exchange.
  That Shiprocket placeholder is to be replaced by Bigship.
- Pincode checker is a labelled local rule (5-day estimate), not a
  courier confirmation. No serviceability API, no courier allocation,
  no shipment creation, no AWB, no label, no tracking link on the order page.
- Without this, paid orders cannot be fulfilled through the site.
- Bigship (per its site): Pan-India, 29,000+ pincodes, 19+ courier
  partners, COD + prepaid, label after booking, dimensions + actual
  weight required for every shipment, API integration with support/training
  from Bigship. API credentials and exact endpoints come from the
  seller's Bigship account/POC — they are not public Shiprocket-style docs.

### 2. No order fulfilment workflow in admin
- Admin home is read-only reporting (recent 20 orders, revenue, low rolls).
- No admin page/API to move an order PLACED → CONFIRMED → PROCESSING →
  PACKED → SHIPPED → OUT_FOR_DELIVERY → DELIVERED, or to record a courier
  / AWB / tracking number. Cancel exists, status progression does not.
- Customer order page therefore never shows real shipment progress.

### 3. No email sending
- Verification and reset tokens are dev-only in non-production and are
  shown in the UI in dev. In production they are not returned, so without
  an email provider a customer cannot verify, reset, or receive order
  confirmation / shipped / delivered mail.
- Needs a provider (e.g. SMTP/Resend), templates, and a send log, before
  accounts can be relied on live.

### 4. Product images are placeholders
- 8 SVG motifs in `public/patterns/*.svg`, honestly labelled on the
  product page as "locally generated textile motif … not a photograph".
- Replace with real product photography before launch; do not present
  an SVG as a photo of stock. No image upload in admin product form yet
  (image is a URL/string field).

### 5. Returns workflow is policy only
- Returns page states the principle (ready-made reviewed, cut fabric
  reviewed with photo evidence, correctly cut lengths treated differently)
  and notes final wording needs adviser review.
- No customer return request form, no photo upload, no admin return
  review / approval / refund-from-return flow. Cancel + refund intents
  exist, returns do not.

### 6. Production database is not the runtime database
- Runtime is SQLite (`src/lib/db.ts`, `node:sqlite`, `dev.db`).
  `prisma/schema.prisma` is a Postgres design on paper, not used at runtime.
- This blocks Vercel/Netlify serverless deployment (ephemeral filesystem)
  and needs either (a) a single persistent-disk server, or (b) a Postgres
  refactor, before permanent deployment. Deployment is therefore the
  last step, after the site is full — as decided 28 Oct 2026.

### 7. Production hardening still open
- No security headers in `next.config.mjs` (only `reactStrictMode`).
- No sitemap / robots.txt / structured data (SEO). Metadata title +
  description exist on the layout, nothing else.
- No rate-limiting/CSRF review beyond existing login rate limit and
  admin token gate. Admin is a single shared token, not role-based
  staff accounts (README notes this).
- Unpaid-prepaid expiry endpoint exists but needs a scheduler secret
  before public exposure; currently admin-cookie only.
- No analytics beyond admin revenue/orders/low-rolls. No Playwright
  end-to-end tests (unit tests only). No concurrent-purchase load test.

### 8. Webhook — closed, not verified live
- Live payment and refund are verified. Webhook delivery to a public
  URL is not: the Cloudflare quick tunnel returned 403 from outside,
  Razorpay auto-disabled the webhook (41 events, last update 28 Oct
  18:02), and the tunnel URL is now dead ("no such host").
  User closed this work 28 Oct 2026. Re-test only after a permanent
  host exists, with the webhook re-registered to that permanent URL.

## Recommended build order (to make it full, then deploy last)

1. Shiprocket live: serviceability, shipment, AWB, tracking on order page.
2. Admin fulfilment workflow: status progression + courier/AWB entry.
3. Email: provider + order/account templates.
4. Real photos: upload + replace SVGs.
5. Returns request workflow.
6. Postgres refactor + security headers + SEO, as deployment preparation.
7. Deploy to a permanent host, then re-register Razorpay webhook and
   re-test it, then switch test keys to live keys only after that checklist.
